# Framework — studio site

Static one-page site built from the `Framework Website Design` canvas
(`Framework Website Design/Framework Site.dc.html`). No build step: plain HTML, one
stylesheet, one script, SVG assets.

```
index.html                          markup for every section
blocks.html                         block-art reference sheet (noindex, unlinked)
post-generator.html                 internal post generator (noindex, unlinked)
assets/post/                        the post generator — see below
test/                               node --test suites for the pure modules
robots.txt                          disallows /post-generator and /blocks
styles.css                          tokens, layout, motion, responsive rules
assets/motion.js                    scroll setup, reveals, marquee, header progress
assets/blocks.js                    block-art geometry + flat SVG renderer — see below
assets/blocks3d.js                  same art rendered in WebGL, with cast shadows
assets/vendor/locomotive-scroll-5.0.1.min.js   Locomotive Scroll v5.0.1 (MIT), lenis bundled
assets/vendor/three-0.185.1/        three.js r185.1 (MIT) — keep both files together
assets/hero-blocks.svg              generated by blocks.js, do not hand-edit
assets/og.png                       1200×630 social share image
assets/favicon.svg                  "F" mark
vercel.json                         clean URLs, cache policy, security headers
```

## Motion

Direction is "Scaffold": the page assembles itself the way the studio builds a site —
hairlines draw first, then content slides up into the frame they just made. Hard easing,
no fades, no blur, no bounce.

Two primitives cover almost everything, so new sections inherit the language for free:

- `.mask` — wraps a block, clips it, slides the child up from behind the edge.
- `.wipe` — hard-edged clip reveal. `.wipe--up` grows from the bottom, `.wipe--right`
  from the right edge.

Both fire when their `.reveal` ancestor gets `.is-in`, and both read a per-element
`--d` delay set inline in the markup, which is how the stagger is tuned. Structural
hairlines use `.rule` + `.rule--top` / `.rule--bottom`; they are pseudo-elements that
scale in from the left rather than static borders.

Locomotive Scroll v5 (Lenis) drives smooth scrolling, the `data-scroll-to` anchor jumps,
the hero parallax (`data-scroll-speed`) and the velocity that pushes the marquee.
Reveals are triggered by a plain IntersectionObserver in `motion.js` so a section always
resolves even when an anchor jump skips past it.

Every motion state is gated behind `html.motion`, set in a head script only when the
visitor has not asked for reduced motion, with a 3-second failsafe that removes the class
if `motion.js` never reports in. Without JS the page renders complete and static.

## Block art

`assets/blocks.js` draws the axonometric white-block sculptures. It is the single
source for the hero, the social exports and anything else that needs the mark's 3D
vocabulary. No dependencies, no build step — it runs in the browser and in Node.

```html
<script src="/assets/blocks.js"></script>
<fw-blocks composition="tower" ratio="9:16" theme="ink"></fw-blocks>
```

```js
FrameworkBlocks.svg({ composition: 'row', ratio: '1:1' })   // SVG string, for rasterising
FrameworkBlocks.element({ composition: 'gate' })            // live SVGElement
```

```sh
node assets/blocks.js --composition mark --ratio auto --yaw-range 1.25 \
  --label "The Framework F, formed by nine blocks that only line up from this angle" \
  > assets/hero-blocks.svg
```

| Option | Values |
| --- | --- |
| `composition` | `mark`, `stack`, `row`, `tower`, `gate`, `random`, or your own array of boxes |
| `ratio` | `"3:4"`, `"1:1"`, `"4:5"`, `"9:16"`, a number, or `"auto"` to keep the composition's own shape |
| `theme` | `paper` (light ground) or `ink` (dark ground), or a palette object |
| `seed` | integer — `random` is deterministic, so a seed always redraws the same sculpture |
| `shadow` | `false` drops the ground shadows |
| `yawRange` | radians, or `[from, to]` — hold the composition, shadow included, in frame right through a turn the rendered version will give it. Framing only; nothing is drawn turned |
| `style` | `hatch` (default) or `flat` — `flat` is the plain three-tone version |
| `padding` | fit multiplier around the geometry, default `1.16` |

Output is byte-identical for identical options, so generated files diff cleanly.

Geometry lives in an `(a, b, z)` grid: `a` runs right-and-down, `b` runs left-and-down,
`z` runs up. A box is `{ a, b, da, db, h, z }` — a corner plus a size — so a composition
reads as a list of solids. Order the list back to front; anything stacked goes after the
box it rests on.

A raised box does not throw a shadow on the floor, because a raised box is normally
resting on the one below and its shadow belongs on *that*. `cast: true` is the exception,
for a solid genuinely hanging over open ground.

### `mark` — the hero, and the one composition that lies

`mark` is the studio's F, laid flat on the ground as nine bars on a nine-by-eight grid of
modules — and then each bar pushed a different distance out along `(1, 1, 1)`.

That direction is the whole trick. The projection is true isometric, so `(1, 1, 1)` is
the camera's own axis: a solid can travel along it as far as you like without moving a
pixel on screen. From one angle, and only that one, the nine bars line up into the mark
exactly. They are nowhere near each other. Turn the sculpture a fraction of a radian and
the letter falls apart into a drift of loose beams.

`motion.js` turns it on a loop rather than off the scroll position, and it runs pile
first: open on a heap of loose bars, turn seventy-odd degrees until they resolve into the
letter, hold there longest, come apart again. That way round because the half worth
watching is the heap turning out to have been the mark all along, and you only get that
if the heap comes first.

Which means the canvas opens on a frame the flat SVG cannot match — the SVG is always the
resolved letter — so the swap is a 600ms dissolve rather than a cut, and reads as the
sculpture turning instead of the art glitching. Reduced motion never reaches any of it:
the whole rendered upgrade sits behind `html.motion`, so that visitor keeps the SVG,
which is the letter.

Three things worth keeping in mind before editing it:

- **Every bar carries `cast: true`.** They hang in mid-air, so without it the flat
  renderer would draw no shadow at all while the WebGL one drew nine. The shadows are
  half the pleasure of it: nine slabs scattered across the floor that plainly cannot have
  been thrown by an F.
- **Both renderers frame for the same turn, shadow included.** A bar hanging in mid-air
  throws its shadow well off to one side, and swings it further still as the sculpture
  turns, so the frame has to hold every solid *and* every shadow at every angle. Miss that
  and a shadow gets sliced off mid-turn against nothing, in the middle of the panel. The
  hero SVG is generated with `--yaw-range 1.25`; `motion.js` passes the matching
  `yawRange` and `shadowRoom: 1`. Change `TURN` in `motion.js` and the SVG has to be
  regenerated to match, or the art will visibly resize the moment the canvas takes over.
- **`lift` counts `LIFT` steps, not modules.** A module a step and the bars fly so far
  apart that their swinging shadows drag the frame open and shrink the letter inside it by
  a fifth. Three fifths of a module leaves the pile at the far end of the turn every bit
  as loose — seventy degrees does that work now — and keeps the shadows close enough to
  frame. Raising `TURN` is the cheap way to a messier pile; raising `lift` is the
  expensive one.
- **The two renderers have to agree on the camera to the last decimal.** They do now, but
  the WebGL camera used to sit at 30° elevation against the SVG's true isometric 35.26°.
  Nothing else in the set noticed the difference. This composition falls apart at it.

Both renderers draw the same engraving, because the flat one is what paints before
three.js arrives — if only the WebGL version were hatched, the hero would visibly jump
from flat art to engraved art on every load. The SVG matches the line frequency, the
light direction, the cross-hatched cast shadow and the stroked face edges of the
rendered version. The contour is why `hatch` sets `outline` by default — the SVG strokes
every face polygon, so the WebGL pass has to as well.

One asymmetry is deliberate: the contour is drawn only where a pixel is a solid. The SVG
strokes box faces but leaves the cast shadow unstroked, so outlining the shadow's edge in
WebGL would not have matched it.

### Rendered version

`assets/blocks3d.js` draws the same boxes in WebGL so the solids cast real shadows.
Lighting is deliberately brutal — one hard directional key, unfiltered shadow maps
(`BasicShadowMap`, never PCF, which would round the edges off), nothing in the scene
carrying colour. A box shows this camera three faces and the key is swung so each catches
a different amount of it: white top, mid-grey side, near-black side, black cast shadow.
Aiming the light at 45° between the two side faces makes both the same brightness and the
form goes flat, which is why it sits where it does.

```html
<script src="/assets/blocks.js"></script>          <!-- geometry, load first -->
<script type="module" src="/assets/blocks3d.js"></script>
<fw-blocks-3d composition="tower" ratio="9:16" theme="ink"></fw-blocks-3d>
```

```js
import { renderToDataURL, createSculpture, supported } from '/assets/blocks3d.js';
renderToDataURL({ composition: 'row', theme: 'ink', width: 1080, height: 1350 });
```

**Treatment.** The straight render goes to a render target and one full-screen pass
re-inks it, which is what lets a cast shadow become a texture rather than a fill.
`style` picks the treatment:

| `style` | What it does |
| --- | --- |
| `hatch` | **Default.** 135° engraving lines thickening as tone drops, cross-hatched in the darkest quarter — the same angle as the striped panels behind the sculpture. Contoured, matching the SVG's stroked faces. |
| `cel` | Four hard tone steps with an inked contour. The only one that keeps real greys. |
| `halftone` | 45° dot screen, dot area by tone. Wants ≥400px or the grid aliases. |
| `dither` | 8×8 ordered dither, one bit. Pixel-locked, so it crawls if the art moves. |
| `plain` | No treatment — flat tones, solid shadow. |

Every screen is capped below solid and the cast shadow is given a tone floor, so the
texture survives into the shadow instead of filling black exactly where it matters most.

Extra options on top of the shared ones: `shadowRoom` (0–1, how much of the cast shadow
the framing makes room for — below 1 the tip runs off the edge and the solids stay
large), `yawRange` (as on the flat renderer, and the two have to be given the same one), `outline` (on by default for `hatch` and `cel`; set `false` to drop it, `true` to add it to any other style), and `yaw` on the export, in
radians.

Two things worth knowing before building on it:

- **Every sculpture shares one WebGL context** and blits into its own 2D canvas.
  Browsers drop the oldest context once a page holds a dozen or so, so a builder with a
  grid of previews would otherwise start losing them.
- **Shadow maps are sized from the output**, 1024 to 4096. A fixed 4096² depth texture
  is about 67MB, which a dozen previews cannot afford.

three.js is ~190KB gzipped, so the site never blocks on it: the hero ships the flat SVG,
and `motion.js` swaps in the rendered version once the page is idle — skipped entirely on
`save-data`, without WebGL, or under reduced motion.

Open `/blocks` to see every composition, theme and ratio, flat and rendered, plus a row
of seeded variants. That page is the starting point for the Instagram post builder.

## Caching

Filenames here are not content-hashed, so everything is served
`max-age=0, s-maxage=31536000, must-revalidate`: the CDN keeps serving from cache and
Vercel purges it on deploy, while browsers revalidate and pick changes up immediately.
The one exception is `assets/vendor/`, which is `immutable` — those filenames carry
their version, so ship an upgrade by adding the new file and updating the script tag.

Do not put a long `immutable` cache back on `/assets/*`. It pins returning visitors to a
stale `motion.js` for a year.

## Post generator

`/post-generator` composes a templated Instagram post — block artwork plus text set in
the studio's own type — and exports it at all three sizes Instagram uses. Internal tool:
unlinked, noindexed, disallowed in `robots.txt`.

Design and plan: `docs/superpowers/specs/2026-08-21-post-generator-design.md` and
`docs/superpowers/plans/2026-08-21-post-generator.md`.

### The document

One plain object describes a post completely. It is the draft in `localStorage`, the
payload in the share URL, and the only input to rendering — nothing else holds state.

```js
{ v: 1, layout, theme, eyebrow, headline, footer, art: { composition, seed }, preview }
```

Everything enters through `normalise()`, so a truncated share link or a hostile hash
becomes a valid default document rather than an exception.

### Modules

| File | Responsibility |
| --- | --- |
| `assets/post/state.js` | Defaults, validation, URL encode/decode, draft. Pure, UMD, tested. |
| `assets/post/layouts.js` | Document + canvas size → draw ops. Pure, UMD, tested. |
| `assets/post/render.js` | Ops → pixels. Art cache, role→hex, text metrics. ES module. |
| `assets/post/app.js` | Form, previews, share link, export. ES module. |

`state.js` and `layouts.js` are pure so they can be tested in Node. `layouts.js` takes a
`measure(text, font)` function as an argument rather than importing one: line breaking
needs text metrics and metrics need a canvas, so inverting that dependency is what keeps
the module free of the DOM.

Script order in the page matters — `blocks.js`, `state.js` and `layouts.js` are classic
scripts and run before the deferred modules, so their globals exist by the time `app.js`
starts.

### Adding a layout

Write a function `(doc, size, measure, u, warnings) -> ops`, add it to `BUILDERS` and its
name to `LAYOUTS` in `layouts.js`, and add the name to `LAYOUTS` in `state.js`. The test
that walks every layout at every ratio will pick it up automatically and fail if any op
escapes the frame.

Sizes go through `u()`, never raw pixels — one unit is `width / 1080`. That is what gives
1:1 and 9:16 the same optical type size. Colours are referenced by role (`bg`, `fg`,
`muted`, `panel`, `bar`, `barFg`); `render.js` owns the hex.

The eyebrow and the footer are the same rank of label and share one spec at 22u mono,
tracking 0.18em. Build them with `label(u)`, never `mono()` directly — they were two
separate constants once and drifted to different sizes. A test now asserts they match in
every layout and every ratio.

Artwork runs to the edges rather than sitting inside the text margin, and in
`headline-above` it reaches the bottom of the post with the footer overlaying it. Any box
edge short of the post's own crops the cast shadow along an invisible line, which reads
as a mistake rather than a bleed. `split` is the exception: its panel is a deliberate
visual edge, so cropping there looks intended.

### Four things that will bite

- **The composition list is derived from `blocks.js`**, with a literal fallback for Node.
  A test asserts the two match, because a stale list silently resets a valid post to the
  default — which is exactly what happened when `mark` was added.
- **Export hands back the live preview canvas**, it does not paint a second one. Chrome
  rasterises text differently on a composited canvas than on a detached one, so a
  re-rendered export drifted from the preview by a level or two of antialiasing. Same
  canvas, no drift, and it is faster.
- **Export writes a data URL, not an object URL.** The object-URL version revoked
  synchronously after `click()`, which tears the blob down before the browser has read
  it — the save then fails or loses its filename, and with it the `.png`. Chrome happened
  to tolerate the race; other browsers do not. A data URL has no lifetime to get wrong.
  The downloads are also spaced ~350ms apart, because browsers throttle saves fired in a
  tight loop.
- **Never size a preview canvas with `width:auto; height:auto` plus both `max-width` and
  `max-height`.** Chrome applies the two maxima independently instead of preserving the
  ratio, and a 1080×1350 preview came out 721×750 — a 20% horizontal stretch, so the
  artwork was warped in the exact view you compose against. Constrain one axis and derive
  the other: `aspect-ratio` plus `width: min(100%, calc(<height cap> * var(--ar)))`, with
  `--ar` set from the backing store in `app.js`. `object-fit: contain` is there as a
  backstop so any future mistake letterboxes rather than warps.

### Tests

```sh
node --test test/
```

`render.js` and `app.js` are verified in the browser rather than in Node — screenshots
and pixel probes, the approach that caught the mirrored axis mapping and the missing
shadow-camera transform in the block art.

### Access

There is none, and that is deliberate. On a static site client-side auth is not a
security boundary: the page and its JavaScript are public whatever a login form does.
When `/post-generator` needs protecting it has to be enforced at the edge — Vercel
Deployment Protection on the path is a configuration change and needs no code.
